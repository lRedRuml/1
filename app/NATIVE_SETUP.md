# Настройка туннеля на каждой платформе (после `flutter_vless`)

Dart-часть готова: `lib/services/tunnel_service.dart` реально вызывает
`initializeVless → requestPermission → startVless/stopVless`, а
`connect_screen.dart` показывает живой статус (задержка, RX/TX, таймер) из
`VlessStatus`. Но **сама Dart-обвязка не запустит VPN**, пока на каждой
платформе не выполнены нативные шаги.

## 0. Почему не было android/ios/macos/windows и как это чинится через GitHub Actions

В этой среде (где писался код) нет ни Flutter SDK, ни сети — `flutter
create` физически нельзя было запустить, весь `lib/` написан вручную
текстом. Решение — переложить это на GitHub Actions, у которого Flutter
SDK ставится автоматически на раннере:

1. Запушь этот репозиторий на GitHub как есть (с `.github/workflows/`).
2. Вкладка **Actions** → выбери **Scaffold native platforms** → **Run
   workflow** (вручную, один раз). Он выполнит `flutter create .` и
   закоммитит сгенерированные `app/android`, `app/ios`, `app/macos`,
   `app/windows` и т.д. обратно в ветку.
3. После этого при каждом пуше в `main` (или вручную) отработает **Build
   Android APK** и положит готовый `.apk` во вкладке Actions → в артефакты
   запуска — скачивается прямо оттуда, локальный Android Studio для этого
   не нужен.

**Важно про подпись APK:** `flutter build apk --release` без отдельно
настроенного ключа подписывает APK debug-ключом — этого достаточно, чтобы
установить APK и проверить, что всё работает, но **Google Play такую
сборку не примет**. Перед публикацией в Play Store нужно:
- сгенерировать свой upload-keystore (`keytool -genkey ...`),
- добавить его содержимое и пароли в Secrets репозитория,
- прописать `signingConfig` в `app/android/app/build.gradle`,
- обновить `build-android.yml`, чтобы шаг сборки использовал этот ключ.

Это отдельный шаг с твоими реальными данными (пароли ключа нельзя класть в
код) — могу подготовить workflow под него, когда решишь публиковаться, но
сам ключ и пароли должны сгенерировать и сохранить в Secrets ты.

Если предпочитаешь собирать локально, а не через CI — тот же результат
даёт:
```bash
cd app
flutter create --org su.vpnonline --project-name vpnonline_app .
flutter pub get
```
Дальше — платформенные шаги ниже одинаковы что для CI, что для локальной
сборки (App Group/Network Extension в Xcode всё равно настраиваются руками,
CI это не автоматизирует).

## 1. Android

[ИСПРАВЛЕНО — критический баг] Раньше `android/app/build.gradle.kts` не
задавал ничего из этого явно, из-за чего кнопка "Подключить" не давала
никакого эффекта на реальном телефоне (VPN вообще не поднимался). Теперь
оба пункта уже прописаны в `build.gradle.kts` (сверься с ним, если менял
файл вручную/пересоздавал проект через `flutter create`):
- `minSdk` — пакет требует минимум API 23 (см.
  `doc/platform/android.md` в репозитории плагина на момент твоей версии —
  минимальная версия могла измениться); `flutter.minSdkVersion` по
  умолчанию может быть ниже.
- `packaging { jniLibs { useLegacyPackaging = true } }` в блоке `android {}`
  — без этого AGP пакует нативные `libxray.so`/`libtun2socks.so` из плагина
  сжатыми внутри APK, рантайм не может их распаковать на части
  устройств/версий Android, и запуск туннеля молча падает без единой
  ошибки в UI (ровно та жалоба "нажимаю Подключить — ничего не
  происходит").
- Убедись, что `mipmap/ic_launcher` существует (используется для
  уведомления foreground-сервиса — уже указано в `tunnel_service.dart`).
- [НОВОЕ] Для реального списка приложений на экране split-tunnel
  (`installed_apps`, см. pubspec.yaml) добавь в
  `android/app/src/main/AndroidManifest.xml`:
  `<uses-permission android:name="android.permission.QUERY_ALL_PACKAGES"
  tools:ignore="QueryAllPackagesPermission"/>` — это чувствительное
  разрешение, Google Play при публикации попросит обосновать его нужность
  в консоли (Policy → Permissions declaration): обоснование "приложение
  показывает список установленных приложений пользователю для настройки
  split-tunneling VPN" обычно достаточно, это ровно тот случай, для
  которого разрешение и существует. Без него `InstalledApps.getInstalledApps()`
  либо вернёт пустой список, либо кинет исключение — экран это уже
  обрабатывает и покажет текст ошибки вместо краша.
- Собери и поставь на реальный телефon (эмулятору для VPN-режима нужен
  отдельный пакет `flutter_vless_android_emulator`, если тестируешь без
  устройства): `flutter run -d android`.
- Проверка: нажми "Подключить" → должен появиться системный диалог
  "Разрешить VPN-подключение" → после разрешения — уведомление о VPN в
  шторке Android.

## 2. iOS / macOS — самая ручная часть, только через Xcode

VPN на iOS работает не как обычный код приложения, а как отдельное
системное расширение (**Network Extension** / Packet Tunnel Provider). Это
**обязательно** для App Store — файлом это не настраивается:

1. Открой `ios/Runner.xcworkspace` в Xcode.
2. Apple Developer аккаунт → создай **App Group**, например
   `group.su.vpnonline.vpnonline_app` — ровно то, что передано в
   `tunnel_service.dart` (`groupIdentifier`). Основное приложение получит
   applicationId `su.vpnonline.vpnonline_app` (org `su.vpnonline` +
   имя проекта `vpnonline_app` из `flutter create`).
3. File → New → Target → **Network Extension** → Packet Tunnel Provider.
   Дай ему bundle id вида `su.vpnonline.vpnonline_app.Tunnel`.
4. Включи тот же App Group в Signing & Capabilities и у основного таргета
   Runner, и у нового Tunnel-таргета.
5. Повтори для `macos/Runner.xcworkspace`, если нужен macOS-клиент.
6. **Тестируется только на реальном устройстве** — симулятор iOS не умеет
   поднимать системный VPN-туннель. Нужен платный Apple Developer аккаунт
   (Network Extension entitlement не выдаётся на бесплатном).

Подробности — `doc/platform/ios.md` и `doc/platform/macos.md` в репозитории
`flutter_vless` (там же — что именно должно попасть в `Info.plist` и
entitlements).

## 3. Windows

Судя по документации пакета, для Windows нужен собственный `xray.exe`
рядом со сборкой (пакет не встраивает бинарник автоматически на этой
платформе) — как именно и куда именно его класть, смотри
`doc/platform/windows.md` в репозитории плагина. Тоннельный режим может
попросить права администратора при первом запуске (системная маршрутизация).

## 4. Что реально проверить перед тем, как звать первого живого клиента

- [ ] Ключ из `/v1/keys` действительно отдаёт рабочий `subscription_url`,
      и GET по нему возвращает то, что `FlutterVless.parseMany()` умеет
      разобрать (проверь вручную — например `curl` этот URL и посмотри
      на формат ответа: голый список ссылок или base64).
- [ ] На Android: подключение реально проходит через сервер (проверь IP
      через браузер на телефоне до/после подключения — он должен
      измениться на IP выбранной локации).
- [ ] Отключение (`stopVless`) реально гасит VPN-иконку в шторке — не
      остаётся "подключено" в интерфейсе при разорванном туннеле.
- [ ] Повторное подключение после потери сети/сворачивания приложения не
      подвешивает `_connecting` в true навсегда (если увидишь такое на
      реальном устройстве — это баг в обработке статусов, присылай лог).

Если на каком-то из этих пунктов что-то не сработает на реальном
устройстве — пришли, что именно происходит (текст ошибки/скриншот), и я
поправлю `tunnel_service.dart`/`connect_screen.dart` под конкретную
причину, а не вслепую.
